# Project Context

## Purpose
Local-first, household-first personal finance management application. Its core is **evidence-driven transaction classification**: every transaction resolves to a category — or a split across several categories — backed by typed evidence, using cheap deterministic rules for the obvious cases and an agentic workflow (receipt retrieval from household mailboxes + a local LLM) for the non-obvious, multi-item ones. Built for a single household initially, with clean seams for later multi-user expansion.

## Tech Stack
- **Backend:** Python 3.11+ with FastAPI
- **Frontend:** React with TypeScript (Vite)
- **Mobile:** Expo / React Native (iOS-first Quiet Ledger client)
- **Database:** PostgreSQL, hosted on `gb10.local`; local-first, not cloud-hosted
- **AI / LLM:** Local on-prem model on `gb10.local` for agentic classification and receipt extraction; cloud LLM (OpenAI, default `gpt-5.6-luna`) used only where explicitly chosen for a specific task
- **Hosting:** Self-hosted on `gb10.local` — the application, PostgreSQL, and the LLM are co-located on one machine, so financial data and mailbox content never leave the host
- **API Style:** RESTful with OpenAPI documentation (auto-generated by FastAPI)

## Project Conventions

### Code Style
- **Python:** Follow PEP 8, use `black` for formatting, `ruff` for linting, `mypy` for type checking
- **TypeScript/React:** Use ESLint + Prettier, functional components with hooks
- **Naming:** snake_case for Python, camelCase for TypeScript/JavaScript
- **Type hints:** Required for all Python functions, strict TypeScript mode enabled

### Architecture Patterns
- **Backend:** Repository pattern for data access, service layer for business logic
- **Classification core:** Separate messy/agentic **evidence gathering** from a deterministic **evidence policy**. Gatherers emit typed `Evidence` and never decide; the policy maps evidence to a categorization as a pure, deterministic, exhaustively testable function. Strength is expressed as discrete tiers (`PROOF/STRONG/WEAK/NONE`), combined max-not-sum; splits require itemized `PROOF`.
- **Learning:** An asynchronous shadow learner turns confirmed outcomes into deterministic rules; it may optimize gatherers/prompts but never silently changes the policy gate.
- **Frontend:** Component-based architecture, custom hooks for shared logic
- **API:** RESTful endpoints, consistent error responses, versioned API paths

### Testing Strategy
- **Approach:** Strict Test-Driven Development (TDD)
- **Python:** pytest with high coverage requirements (>80%)
- **React:** Vitest + React Testing Library
- **Integration:** API endpoint tests with a test database
- **Policy layer:** Exhaustive unit tests over evidence permutations (determinism, strongest-governs, no-accumulation, itemized invariant, contested routing)
- **Requirement:** Tests must pass before merging any PR

## Domain Context
- **Transactions:** Income and expenses with categories, dates, and amounts
- **Categorization:** Always a set of splits `(amount, category, evidence)` summing to the transaction total; a single category is the `N=1` case
- **Evidence:** Typed support for every decision (rule, history, web lookup, receipt, LLM inference), carrying a strength tier and an `itemized` flag
- **Mailboxes:** Multiple household mailboxes; the paying person is not always known up front, so receipt search spans mailboxes within a time window
- **Budgets:** Monthly spending limits per category
- **Accounts:** Shared household bank accounts, credit cards, cash tracking
- **Goals:** Savings targets with progress tracking
- **Currency:** Single currency support initially (expandable)

## Important Constraints
- **Local-first:** runs on a single self-hosted machine, `gb10.local`, where the application, PostgreSQL, and the LLM are co-located; any cloud service is additive, never required
- **Privacy:** financial data and raw mailbox content stay on `gb10.local` and are processed only by the on-prem local LLM; nothing is sent to a third-party/cloud service
- **Household-first:** designed for one shared household now, with data boundaries that do not assume a single global household (seams for later multi-user)
- **Decimal accuracy:** financial amounts use exact decimal handling (avoid floating point)
- **Auditability:** every applied categorization references the evidence chain that justified it

## External Dependencies
- **PostgreSQL on `gb10.local`:** primary data store
- **Local LLM on `gb10.local`:** receipt extraction, triage, and agentic classification
- **Household mailboxes:** read access for receipt-evidence retrieval
- **OpenAI (optional, cloud):** used only for tasks explicitly chosen to run on a cloud model (default `gpt-5.6-luna`)
- **Azure (deferred):** Terraform infra exists in `infra/`, but cloud deployment is out of scope for the local-first direction
